# Figma Semantic Bridge v0.5.0 — replacement architecture and implementation contract

Status: proposed, planning only. Target: **replace the v0.4 product path**, not incrementally extend it. Baseline: v0.4.0 alpha; preserve its tag and main history. Implementation must begin on a separate `feat/v0.5-core` branch after review. This document is the authoritative scope for v0.5.

## 1. Product contract and non-goals

Bridge is a **human-authored semantic overlay on Figma node references**. The coding agent, using Figma MCP, is responsible for retrieving Figma design structure, text and visual details and for Fig2Code. Bridge does not replicate Figma or generate code.

Successful user journey:
1. Start a local CLI server and open its browser UI. No macOS native wrapper.
2. Create/select/delete a workspace. With no active workspace, no editor; inbound sends receive a clear rejection.
3. Workspace shows **Canvas** and **Regions** tabs, initially empty with instructions: select a node in Figma Dev Mode, open the Bridge plugin, send as UI or Spec.
4. Plugin reads the *current native Figma selection* and posts **one selected node at a time** to a fixed localhost endpoint. Send file key, page ID, node ID, kind, absolute BBox, preview PNG and optionally a text hint. No enclosing-frame selection, document scan, pairing, token, persistent connection or workspace selector in plugin. The active workspace belongs exclusively to the server.
5. Canvas displays the transferred node images at their original Figma absolute coordinates, partitioned by file/page with a vertical selector. Never overlay unrelated file/page coordinate systems. Pan/zoom/fit, select, resize/reposition local semantic bounds where needed, delete, and immediately type a name for the selected region. UI/Spec tool selection is available; all edits autosave.
6. Regions tab displays independently scrollable **side-by-side** UI and Spec lists. UI entries show BBox-cropped image previews; Spec entries show text hints if available, otherwise names. UI entries can be reordered and nested without depth limit, with one UI parent and no cycles. Spec entries remain in the Spec list while ghost references can be dragged under multiple UI entries; dropping creates/removes relations, not copies. UI cannot nest under Spec. UI↔Spec is many-to-many, including across Figma files/pages. No mandatory bottom drawer, source matching or approval.
7. Canvas and Regions are peer views of the same live autosaved workspace; editing order is unrestricted. Selection and scroll position should be preserved across tab changes when practical.
8. Export semantic nodes, stable Figma references, UI hierarchy and UI↔Spec relations as JSON, and expose the same via a small read-only MCP surface.
9. Coding agent uses the reference and Figma MCP to read actual node structure/content. Bridge does not export Figma node trees, raw specification text or screenshots as semantic output.

**Node identity:** `fileKey + nodeId` is the remote Figma lookup identity; retain `pageId` for provenance and canvas partition. Store a usable original Figma node URL when available, or construct/verify a canonical URL. Bridge internal IDs must be independent of Figma IDs, so relationships and repeated references are unambiguous. If the same Figma node is sent twice, use a documented, tested deterministic policy (default: update snapshot of existing region of same kind and identity, preserve user name/relationships; different kind may coexist). Never silently delete user edits.

**Spec semantics:** A Spec is a reference to a selected Figma node with a human-assigned semantic name/description and relations. Extracted text is **only local preview/relationship-assistance data**, not authoritative specification content and not part of JSON/MCP semantic output. Figma MCP reads original text. Avoid scanning descendants unless a specifically proven preview need requires it; a non-TEXT selected container may have no text hint.

**Explicit non-goals:** Fig2Code, complete Figma graph extraction, spatial BBox-to-node search, page/frame bulk capture, semantic AI generation, auto-inferred relationships, approval gates, external collaboration, cloud sync, enterprise auth, native app, packaged binaries, import of v0.4's legacy complex data model, speculative plugin features, rich diagnostics dashboard.

## 2. Migration: aggressively retire v0.4 implementation

| v0.4 subsystem | v0.5 disposition | Rationale |
| --- | --- | --- |
| `desktop/` AppKit, WKWebView, signing, DMG/ZIP and native release pipeline | **Delete from v0.5 runtime/build** | Browser served by CLI is sufficient |
| Local HTTP server/bootstrap | **Retain concepts, rewrite thin server** | HTTP static UI + POST + workspace CRUD + JSON + MCP |
| `src/figma/capture.ts` and plugin image export/selection | **Extract minimal proven adapter** | One selected node + PNG + metadata; no DFS |
| `src/figma/structure-reader.ts`, chunk/collection/cursor/replay/recovery and selective acquisition | **Delete from v0.5 path** | No whole-tree collection |
| Geometry helpers / BBox / coordinate mapping | **Reuse small pure functions only after contract tests** | Canvas geometry and image placement |
| `web/App.tsx` giant editor, inspector, source-review and import panels | **Replace, do not refactor in place** | Two-tab product and simpler interaction |
| Annotation/spec/proposal/approval contracts | **Replace with small versioned v0.5 schema** | UI tree + Spec references + N:N edges |
| Pairing token, mutual TLS/HMAC, WebSocket session and reconnection | **Remove from plugin transport** | Stateless HTTP POST; no per-user setup |
| v0.4 proposal provider/AI workflow | **Remove** | Agent does downstream work |
| v0.4 source evidence files, full text, snapshots, approval/export rules | **Do not migrate automatically** | Wrong product contract |
| Existing E2E fixtures and test utilities | **Selectively adapt** | Retain useful browser, plugin and MCP validation patterns |
| v0.4 docs/screenshots | **Archive as historical** | New README and user guide from scratch |

Do not preserve obsolete abstractions just to avoid deleting code. Prefer a clean v0.5 directory layout and new entry points. v0.4 data must remain untouched; v0.5 uses a separate data directory/schema and does not overwrite or silently migrate it. Document any optional future migration as out of scope.

**Branch strategy:** keep main and v0.4 tag intact; implement in `feat/v0.5-core` based on latest main, with a new isolated v0.5 app/package surface (a clean-room-in-repo approach). No need for a separate repository. Merge only after v0.5 E2E acceptance; remove obsolete runtime/build paths in the v0.5 integration PR. Avoid an extended compatibility layer. If the codebase makes isolation infeasible, use a separate orphan/prototype branch and explicitly record the reason before implementation; do not silently rebuild the entire repository.

## 3. Minimal runtime and transport

Target setup: `git clone` → `npm ci` → `npm run build` → `npm start` (or one documented `npx`/CLI command). Server prints local URL, serves static UI, JSON API and stdio MCP entrypoint; no Electron, Swift, browser install, database daemon or external cloud service. Choose simple persistent local JSON or SQLite only after comparing operational complexity; atomic writes and workspace durability are required. Package plugin build output and manifest as local files with one short Figma import instruction. No distribution infrastructure required.

Fixed loopback port with explicit collision error, e.g. 38471, bound to `127.0.0.1`. The plugin knows only the endpoint, not a workspace ID, secret or connection state. POST returns success or a concise actionable error; no handshake or retry queue. Figma manifest must explicitly permit the loopback endpoint. Verify Dev Seat + read-only other-owner file permissions as a separate acceptance gate; do not claim them based on synthetic fixtures.

**Security decision (deliberate, documented):** no pairing/authentication token and no session. This sacrifices protection against malicious local processes. Still enforce loopback-only binding, explicit allowed Origin/CORS handling including preflight, JSON Content-Type, bounded body/image sizes, schema validation, no arbitrary file path/URL fetching, no execution endpoint, and workspace existence check. CORS/Origin are not authentication. If Figma plugin origin behavior conflicts with this, verify and use the narrowest working policy; do not add pairing without explicit product approval. Inbound POST is append/update only; destructive workspace operations are not exposed through the plugin endpoint.

## 4. Data model (small, explicit)

`Workspace { id, name, regions[], relations[], updatedAt }`
`Region { id, kind:'ui'|'spec', figma:{fileKey,pageId,nodeId,url?}, name, description?, bbox, previewAssetId?, textHint?, parentUiId?, order, createdAt, updatedAt }`
`Relation { id, specRegionId, uiRegionId, order? }`

Constraints: only UI can have `parentUiId`; UI parent references UI within same workspace; one parent per UI; unbounded depth; acyclic. Spec regions are independent roots in the Spec list and may be referenced from any number of UI regions; relations are unique per pair. Relations may span Figma files/pages. Preview and textHint are UI-only storage; **exclude from JSON/MCP semantic export** along with bbox unless specifically justified for agent semantics. Semantic output must include name/description, kind, Figma reference, UI hierarchy, ordered siblings and N:N relations. Figma node IDs are opaque; do not treat `nodeId` alone as globally unique.

Image coordinate rules: original absolute BBox determines placement *within file/page partition*; preserve spatial relationships. Do not conflate source BBox with user-adjusted visual/semantic bounds without an explicit model decision. Exported image is a historical snapshot; resending may refresh preview while preserving semantic edits.

## 5. UX contract

**Workspace gate:** only create, choose, delete before selection. Empty selected workspace shows Canvas/Regions tabs and concise Figma send instruction.

**Canvas:** full work area, minimal toolbar for UI/Spec selection and navigation, selected-region handles/delete, inline name input that receives typed text immediately after create/select/resize without unintended keyboard shortcuts. Automatic autosave; no Save button, review wizard, confirmation or candidate-search controls. File/page vertical tabs; stable zoom/pan per partition when useful; fit-to-content for new content. No fabricated spatial relationships across pages.

**Regions:** two horizontally adjacent independently scrollable lists. UI list supports ordered drag/drop hierarchy with visual insertion cues, keyboard-accessible reorder/reparent alternative and cycle rejection. Spec list remains authoritative for every Spec. Dragging a Spec into a UI tree creates a **ghost relation** under that UI; Spec remains in right list and may appear under multiple UI nodes. Dragging a ghost away removes only that relation. Never allow UI beneath Spec. Preview each UI from the transmitted image crop, Spec from text hint or name. Direct inline rename/description, autosave; no mandatory review drawer. Maintain stable focus/scroll across updates.

**No required workflow order:** user can switch tabs, add more nodes, rename, reorganize and export at any time. Empty or partially named regions remain editable. Show missing data as lightweight nonblocking hints, not approval gates. Avoid onboarding tours, redundant status badges, 'find candidates' buttons or developer-oriented explanations.

## 6. Implementation phases and acceptance

**P0 — feasibility gates (before rewriting):** Confirm real Dev Mode plugin reads selected node ID/file/page/BBox and exports PNG on a Dev Seat read-only file; confirm plugin `fetch` to fixed loopback POST and CORS/preflight on Figma Desktop, with no token; confirm Figma MCP can dereference fileKey+nodeId URL independent of current selection. Existing v0.3 image-export success and current Figma MCP usage are prior evidence, not reasons to reimplement them. If any gate fails, record exact failure and minimum viable workaround; do not invent a new transport architecture without review.

**P1 — clean foundation:** Isolated v0.5 schema/storage, CLI/static web server, workspace gate, stateless plugin POST, PNG asset persistence and autosave. Tests: no workspace rejection, valid/invalid requests, same-node resend preservation, port collision, restart persistence, malformed/oversize image, source identity.

**P2 — Canvas:** file/page partition, original-coordinate image placement, select/inline type/rename, local bounds adjustment, deletion, zoom/pan/fit. Tests for negative/fractional coordinates, transforms, cross-page separation, keyboard focus, image error.

**P3 — Regions:** independent side-by-side lists, UI unlimited-depth tree reorder/reparent, Spec ghost N:N drag/drop, cross-file relations, duplicate prevention, unlink versus delete, autosave, keyboard accessibility. Tests for cycles, reparent, stable order, repeated spec relations and persistence.

**P4 — Agent handoff:** stable minimal JSON export and read-only MCP tools for list workspaces, get workspace semantic context and get region/relations. Verify MCP data exactly matches JSON and excludes preview/text hint/raw Figma content. Test agent dereferencing a Figma node using official Figma MCP as an external integration gate.

**P5 — acceptance:** real native Figma selection → plugin one-click UI/Spec send → browser Canvas/Regions → rename/tree/N:N relation → app restart → JSON/MCP → coding-agent Figma lookup. Verify with at least two pages/files, several nested UI regions and one Spec linked to two UI regions. Include negative paths, screenshot review, browser E2E, no hidden dependency on native wrapper or whole-tree scan. Document known Dev Seat permissions separately if not reproducible.

Do not start P2 before P1 transport works; do not claim P5 from mocked Figma alone. CI should run fast unit + browser E2E and CLI smoke tests; native Figma validation is a separately recorded manual/agent test.

## 7. Strict Codex operating constraints

- **Do not implement anything beyond P0–P5 acceptance.** No feature parity mandate with v0.4; deletion is preferred over preservation.
- No new tabs, panes, drawers, review states, approval steps, search/index engines, import budgets, progress dashboards, AI suggestions, multi-user sync, native app, security pairing or background daemon without a demonstrated blocker and explicit owner approval.
- A fix or small supporting feature is allowed **without approval** only if necessary to pass an existing acceptance test or resolve a reproducible blocker, is the smallest local change, introduces no new user-facing workflow, and is documented with test evidence.
- For any material scope extension: write a short decision note with blocker, rejected alternatives, minimal proposal, impact on product contract and required approval; **stop that extension**, continue independent in-scope work. Never silently expand scope in the name of robustness or polish.
- Every phase must end with actual execution evidence, not only code or prose. Prefer end-to-end completion over broad scaffolding. Never declare success with known failed acceptance tests; report exactly what remains and why.
- Avoid 'enterprise-grade' abstractions, future-proof frameworks and speculative configuration. Keep dependencies minimal, preserve a simple CLI startup and clear failure messages.
- Do not modify v0.4 releases, historical data, or main until reviewed merge. Maintain a migration/deletion ledger listing what was removed, retained and replaced.
- Treat security tradeoffs as explicit: do not claim localhost is secure; do not restore token pairing without approval. Avoid transmitting any extra private Figma content beyond the selected node's requested preview and minimal hint.
- On uncertainty, choose the narrower interpretation of the product contract; ask only if an irreversible design or security decision is required.

## 8. Definition of done

A new contributor can clone/build/start from the README without Xcode, a native wrapper, external services or credentials for Bridge; the plugin sends one selected node with a single click and no pairing; a workspace can organize cross-file UI hierarchy and N:N Spec relations with autosave; JSON/MCP expose only human semantic metadata and resolvable Figma references; real Figma and browser tests substantiate the flow. All retired v0.4 paths are absent from the v0.5 runtime. No claim of Fig2Code quality or independent corporate permission validation without separate evidence.
