# v0.5.0 user-task acceptance — executable scenarios

**Normative acceptance contract.** These are tasks a person or coding agent must complete with the real product. Tests must assert persisted data and visible behavior, not merely button presence, callback invocation or similarity to the UX sketch. Use deterministic synthetic fixtures in CI; repeat the primary path in real Figma Dev Mode as a separate release gate. No work may be declared complete while a mandatory scenario fails.

## Test fixture

Two Figma files (`F1`, `F2`), two pages in F1 (`P1`, `P2`), UI nodes A/B/C/D/E and Spec nodes S1/S2. A is an ancestor of B/C in *user-defined semantic hierarchy*, not necessarily in Figma's layer tree. S1 is related to B and D across files; S2 to C. Include negative and fractional absolute coordinates, overlapping bounds and repeated node names. Use real PNGs for plugin/browser integration, generated safe fixtures for CI.

## Mandatory user journeys (Gherkin-style)

**T01 — Workspace gate**
Given a fresh installation with no active workspace, opening the browser shows only workspace create/select/delete; Canvas and Regions are inaccessible. When a plugin POST arrives, it fails with an actionable no-workspace response and does not persist an orphan. After creating and selecting W1, both tabs are visible and empty; reloading retains the workspace. Switching to no workspace blocks edits and inbound sends.

**T02 — One-click stateless Dev Mode transfer**
Given W1 active and Bridge running on loopback, in Figma Dev Mode with a readable selected node A, opening the plugin and clicking UI Send once creates exactly one UI region with fileKey/pageId/nodeId, original BBox and PNG. No token, pairing, workspace selector, reconnect, parent-frame scan or extra confirmation. Repeat for Spec S1. The plugin reports success/failure succinctly. Restart the plugin and send another node without re-pairing. Repeat in a real Dev Seat read-only file if available; if unavailable, mark the gate unverified rather than passing it.

**T03 — Identity, resend and failure safety**
Given A already imported and renamed, sending A again as UI refreshes preview/BBox but retains semantic name, hierarchy and relations; no duplicate UI region. A in a different file identity is distinct. A as Spec follows the documented separate-kind policy. Malformed/oversized payloads, invalid file/node IDs, missing active workspace and unavailable port fail without mutating existing data. Requests must not fetch arbitrary URLs, read local paths or execute commands.

**T04 — Canvas partitions and spatial fidelity**
Given A/B in F1/P1, C in F1/P2 and D in F2/P1, Canvas exposes separate file/page partitions. Each shows only its own nodes with original relative positions and size; no cross-page overlay. Switching partitions preserves the regions. Fit, pan and zoom work with negative/fractional coordinates. Select a region, type a name immediately without clicking a separate Save control, move/resize locally and delete it. Reload: names and bounds persist; keyboard shortcuts do not corrupt name typing.

**T05 — Unrestricted edit order**
Given several imported nodes, rename in Canvas, switch to Regions, reparent UI, return to Canvas, import another Spec, and change a name again. No wizard, mandatory approval, node-candidate search or save/confirm button blocks progress. Changes survive browser reload and server restart. UI list and Spec list scroll independently; switching tabs does not unexpectedly reset active work.

**T06 — UI tree with arbitrary depth**
In Regions, drag A under B, B under C, C under D, and reorder siblings. The resulting UI hierarchy and order persist after restart and appear identically in JSON/MCP. Attempt to move D under A (cycle) and reject without corruption. Attempt to drop UI under Spec and reject. Move B to root; descendants remain intact. Verify both drag-and-drop and an accessible keyboard alternative.

**T07 — Spec ghosts and N:N relations**
Drag S1 from the Spec list under B and D (different Figma files); S1 remains once in the Spec catalog and appears as a ghost under each UI. Link S2 to C. Repeated S1→B drop is idempotent. Unlink S1 ghost under B: relation to D and Spec catalog item remain. Deleting S1 from the catalog removes its relationships only after appropriate destructive confirmation; unrelated UI hierarchy stays intact. Reload and verify all relations.

**T08 — Semantic output boundary**
Given completed T06/T07, export JSON and call read-only MCP for the same workspace. Assert same region IDs, ordered UI tree, stable Figma references, semantic name/description and N:N relations. Assert **no** PNG/base64, textHint, raw Figma TEXT content, style dump, bulk node graph, internal auth tokens or local paths. The coding agent can derive a resolvable Figma node URL using fileKey+nodeId; pageId remains provenance.

**T09 — Real Figma MCP dereference**
Using the actual Figma MCP configured for the coding agent, dereference one UI node and one Spec node from the exported references, without relying on current Figma selection. Verify actual node context/text can be retrieved with the user’s existing access. If unavailable, mark integration as blocked with exact reason; do not add an internal Fig2Code engine as a workaround.

**T10 — CLI setup and runtime isolation**
From a clean checkout: `npm ci`, `npm run build`, `npm start`. Verify printed local URL opens, workspace and plugin receiver work, data survives restart, and a second process on the same port fails clearly. No Xcode, Electron, Swift, DMG, external DB, cloud service, user Bridge credentials or hidden v0.4 runtime dependency. Validate a clean shutdown.

**T11 — Real-world failure and recovery**
Disconnect/close Figma plugin between sends, restart the Bridge server, import a node with an unavailable preview, and send a malformed request. Previously stored regions and relations remain usable; next successful send requires no pairing or recovery wizard. Missing preview has a nonblocking fallback. No false claim of successful send after HTTP failure.

**T12 — Real user comprehension**
Give a new tester only the initial empty-state instruction, not a walkthrough. Ask them to transfer two UI nodes and one Spec, name them, nest one UI under another, link the Spec to both, and export. Record where they hesitate, what UI elements they misunderstand, and whether they can complete the task without explanation of internal state. This is a manual qualitative acceptance gate, not a fabricated numerical usability score. Any task-blocking ambiguity must be fixed and retested.

## Test layers and evidence
- Unit: schema invariants, identity/resend policy, tree cycle prevention, ordering, N:N relation uniqueness, output exclusions, persistence.
- Browser E2E: T01, T03–T08, T11 with actual browser interactions and persisted server state. Test real drag/drop and keyboard flows, not direct store mutation.
- CLI/HTTP integration: T02 simulated plugin payload, T03, T10; real server, CORS/preflight, body limits and loopback binding.
- Native Figma: T02 with actual Dev Mode selection and PNG; T09 with actual Figma MCP; no mock-only success claims.
- Human UX: T12 with recorded observations; design quality is assessed by task completion, not pixel comparison with prototype.

## Exit rule
P0–P5 can close only with test command, environment, commit SHA, pass/fail evidence and explicit unresolved external gates. If any mandatory acceptance fails, fix and rerun. If blocked by unavailable permissions, record 'not verified' and do not call it passed. Any necessary supporting feature must be the smallest change that removes a demonstrated task blocker, with no new workflow. Any new product capability requires explicit approval.
