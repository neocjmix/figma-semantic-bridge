Status: source inspection and official API research, 2026-10-25. No private Figma file, live plugin, or external account was accessed. This is an implementation boundary for the local development plugin, not a claim that a 105,000-node scope has been captured.

## Baseline before ADR 0007

`capture_metadata` pins one selected current-page container ID, traverses its descendants in one plugin request, retains exact source values, and returns an explicit incomplete prefix at a node, byte, or time budget. Its `children` arrays and DFS stack exist only inside that request (`src/figma/capture.ts`). The broker accepts one bounded response, and the acquisition manager persists either that validated result or a partial status. A partial result cannot be committed as a complete source capture (`src/server/acquisition.ts`). There is no continuation command or durable traversal frontier yet.

The current contracts cap one `Snapshot` at 10,000 nodes, one capture request at 10,000 nodes/4 MB metadata/15 seconds, and a WebSocket result at 16 MB (`src/shared/contracts.ts`, `src/figma/bridge-client.ts`). Acquisition journals cap each task at 16 MB and their total at 96 MB; project JSON caps at 48 MB (`src/server/acquisition.ts`, `src/server/store.ts`). Capture bundles cap *all selected scopes together* at 10,000 nodes, 4 MB node JSON, and 15 MB encoded (`src/server/capture-bundle.ts`). Matching, source review, canvas, and project validation currently consume `snapshot.nodes` as one array. Raising only a plugin limit or writing 11 independent snapshots would not prove a complete 105,000-node scope or preserve its existing review semantics.

## Official Figma constraints

- [`children`](https://developers.figma.com/docs/plugins/api/properties/nodes-children/) returns a **new, complete read-only array** on each access, ordered back to front. Figma cautions that manual DFS/BFS that repeatedly reads this property can be slow on large files. The reference does not expose a child offset/page API. A plugin can bound what it *serializes*, but cannot assert a fixed allocation or time bound for reading one extremely wide parent's `children` array.
- [`getNodeByIdAsync`](https://developers.figma.com/docs/plugins/api/figma/#getnodebyidasyncid-string-promisebasenode--null) can rehydrate a serialized node ID; it returns null if the node no longer exists. This supports a persistent ID frontier, not persistence of live node objects.
- With `documentAccess: "dynamic-page"`, [the current page is loaded as needed](https://developers.figma.com/docs/plugins/accessing-document/), and [`PageNode.on('nodechange')`](https://developers.figma.com/docs/plugins/api/properties/PageNode-on/) observes additions, removals, and updates on that page. File-wide [`figma.on('documentchange')`](https://developers.figma.com/docs/plugins/api/properties/figma-on/) requires `loadAllPagesAsync` in dynamic-page mode and batches callbacks asynchronously. Using it would violate this workflow's no-whole-file-load constraint. Page change notifications are useful invalidation signals, but the documentation does not establish an atomic file revision token or gap-free checkpoint across plugin restarts. That last sentence is an inference from the documented API, not a claim that Figma lacks any internal versioning.
- The [plugin close event](https://developers.figma.com/docs/plugins/api/properties/figma-on/) cannot finish asynchronous work; its runtime is destroyed after callbacks return. Durable progress must be acknowledged by the local server *before* closing or replacing a plugin session. A reconnect alone cannot certify that an earlier frontier still describes the same document state.
- The documented [`exportAsync` signature](https://developers.figma.com/docs/plugins/api/properties/nodes-exportasync/) takes export settings and returns a promise; it does not document an abort or native progress parameter. A cooperative deadline can discard a late result, but cannot guarantee that native rendering stops immediately.
- [`figma.fileKey`](https://developers.figma.com/docs/plugins/api/figma/#filekey-string--undefined-readonly) is available to private plugins and local development with [`enablePrivatePluginApi`](https://developers.figma.com/docs/plugins/manifest/#enableprivatepluginapi-boolean), which this repository's local manifest sets. Availability in a public Community plugin is not established and must remain a separate release constraint.
- The separate [REST file-nodes endpoint](https://developers.figma.com/docs/rest-api/file-endpoints/#get-file-nodes) offers explicit IDs, `depth=1`, and `version`; it requires `file_content:read` credentials and can return extra ancestor, top-level, or dependency nodes. It is a possible version-pinned provider, not an interchangeable plugin cursor or proof of bounded response size.

## Initial continuation proposal (superseded by ADR 0007 where different)

1. Create a new versioned **structure job** contract, leaving `SnapshotSchema` and existing captures intact. Pin file key, current page ID, selected root ID, root scalar metadata, coordinate policy, plugin session, requested fields, and task budget. Do not alter Figma selection or request a whole-file dump.
2. Keep the traversal cursor on the local server, not as an untrusted caller-supplied position. Persist a bounded DFS frontier of ancestor node IDs, next-child positions, and the child-order identity observed for every open parent; a job generation, chunk sequence, cumulative counts/bytes, and a durable set/index of emitted IDs prevent duplicates. Do not serialize live Figma node objects. Rehydrate only frontier IDs on the current page and fail if any disappeared, moved, or changed identity.
3. Have the plugin emit one bounded chunk of exact source records and a successor frontier. Account for UTF-8 bytes and record count *before* emitting. If a single `children` read is too costly or violates an observed memory/time policy, stop with a specific `WIDE_PARENT_UNBOUNDED` state; do not silently skip that branch or call the job complete. `findAll` is not a paging substitute because it searches a subtree and returns an array of matches.
4. Atomically validate and persist the chunk, its digest, its frontier, and its cumulative lower-bound progress before acknowledging it. Retry the same sequence idempotently. Cancellation preserves only acknowledged chunks. A plugin timeout or session loss leaves a resumable *proposal* that still needs source revalidation; it is not automatically a continuous observation.
5. Subscribe to page-scoped `nodechange` while the session is active and record an invalidation epoch. Verify root/file/page identity and frontier ancestry/order before and after every chunk. Any observed relevant change invalidates the live cursor or starts a new observation. Because callbacks and session lifetime do not supply an atomic version boundary, strict one-revision tasks need an independently version-pinned provider or a documented uncertainty/reacquisition path. Do not classify unchanged root bounds alone as unchanged descendants.
6. Mark structure complete only when the frontier is empty, all planned branches have acknowledged records, IDs and ancestry are consistent, exact fields are present, cumulative budgets pass, and the job's consistency policy is satisfied. A 10,000-node chunk is complete *for that chunk*; an unvisited frontier is an incomplete scope. If required work cannot continue, surface the precise unfinished branches and preserve earlier validated observations without approval.
7. Before claiming 105,000-node support, design a chunk-aware durable source store and paged read APIs, then update matching, source review, canvas overlays, MCP/source summaries, capture bundles, backup/restore, project limits, and approval gates to use the same scope-completion ledger. Validate synthetic 105,000-node cases, a very wide single parent, restart/reconnect, mutation during traversal, and actual local Figma behavior separately. The current one-array `Snapshot` path remains capped at 10,000.

## Blocker classification

The cursor, server journal, idempotency, indexed source store, consumers, and synthetic tests are engineering work that can be done locally without private designs. There is no identified need to edit source Figma files for them. The official Plugin API does **not** document child pagination or an immutable version token for these plugin reads; a strict same-revision guarantee and bounded native cost for every possible 105,000-node shape cannot be promised from the current plugin path. Live performance and behavior on a real large file remain unverified and require authorized access to an appropriate Figma fixture. A REST version-pinned fallback would require credentials, file permission, explicit provider-equivalence checks, and its own boundedness tests.
